# Xboard 发布审查规程

版本：1.0  
适用范围：Xboard 小型开源项目的功能审查、修改、验证和交付。  
最后更新：2026-07-22

## 1. 基本原则

- 先检查，后修改；没有得到修改要求时只输出检查结果。
- 不进行一次性重写，只处理已经出现的重复、错误和真实使用问题。
- 优先保证插件可构建、可安装、可回退，并尽量保留已有配置。
- 使用 Obsidian 官方公开 API，不依赖未公开内部接口。
- 未经明确确认，不增加网络请求、遥测、云同步或外部服务。
- 未经明确要求，不删除文件、不创建 Git 远程、不提交或推送代码。
- 用户在会话中的最新明确要求覆盖同一事项的较早要求。

## 2. 会话开始

开始工作前必须完成以下事项：

1. 阅读项目根目录的 `AGENTS.md` 及当前任务适用的技能说明。
2. 确认任务属于“检查”“修改”“诊断”还是“交付”。
3. 对较大改动先说明目标、受影响文件和最小可行实现。
4. 检查工作区状态，避免覆盖用户已有修改。
5. 涉及仪表盘 UI 时检查可访问性、移动端触控和信息真实性。

## 3. 第一轮检查

第一轮审查应保持只读，至少检查：

- `src/main.ts`、主要 View、Service、Modal 和设置文件。
- `manifest.json`、`package.json`、TypeScript、ESLint 和构建配置。
- README、LICENSE、贡献说明、更新日志、Issue 模板和发布工作流。
- 硬编码的个人姓名、Vault 路径、文件名、属性名和模拟数据。
- 空数据、错误状态、异步异常、生命周期和移动端兼容性。
- 当前发布物是否与根目录构建产物一致。

审查结果按以下顺序输出：

1. 当前功能。
2. 明显问题。
3. 可保留代码。
4. 必须修改、建议修改和以后再做。
5. 小步提交计划。

## 4. 修改范围确认

开始修改前应记录用户确认的产品要求，例如：

- 插件名称、版本、作者和稳定插件 ID。
- 默认文案与文案是否允许用户编辑。
- 模拟功能是删除、隐藏还是保留并标记。
- 是否需要安装 ZIP、GitHub 源码包或两者都需要。

如果用户在构建过程中修改要求：

1. 让正在运行的非破坏性检查安全结束。
2. 不交付已经过时的构建产物。
3. 按最新要求修改源码。
4. 重新执行构建、检查、复制和哈希验证。

## 5. 产品真实性规则

- 未实现功能可以保留界面预览，但必须直接显示“即将实现！”。
- 预览卡片必须说明不会读取外部数据，不能伪装成实时结果。
- 不使用固定完成率、固定同步时间或虚假的实时状态。
- 未配置、目录不存在、空数据和加载失败必须显示不同状态。
- 错误信息说明发生了什么以及用户下一步可以做什么。
- 卡片只放标题、必要数据、状态和操作，不添加装饰性副标题。

## 6. 配置和兼容性规则

- 新用户默认配置不得包含开发者姓名、私人 Vault 路径或设备专用路径。
- 已保存的有效用户配置应在升级时保留。
- 配置必须有版本号、运行时校验、默认值和小型迁移函数。
- 路径输入应规范化，并尽可能提供 Vault 内目录建议和有效性提示。
- `manifest.json`、`package.json`、发布标签和交付目录中的版本必须一致。
- 声明移动端可安装时，主要触控目标应至少为 44×44 像素。
- 兼容性警告不得静默隐藏；保留警告时应在 README 或交付说明中解释原因。

## 7. 代码修改规则

- 数据读取保留在 Service 中，View 不直接分散读写 Vault 文件。
- 常用创建、打开、任务操作通过小型动作服务复用。
- 卡片 ID、标题、图标、默认尺寸和选择器集中在卡片注册表。
- 只抽象已经重复或容易失配的逻辑，不为未来功能建立大型插件系统。
- 后台文件修改优先使用 `Vault.process()`，路径使用 `normalizePath()`。
- Obsidian 事件使用 `registerEvent()`，长生命周期 DOM 事件使用 `registerDomEvent()`。
- 异步保存、卡片布局、文件打开和计时结果不得留下未处理的 Promise。
- 计时器应依据结束时间计算，不依赖简单的每秒递减。

## 8. 验证顺序

源码修改完成后按顺序执行：

```bash
npm run build
npm run lint
npm audit --omit=dev
```

还应检查：

- TypeScript 构建是否通过。
- ESLint 是否有错误；警告是否已解释。
- 依赖审计是否存在生产漏洞。
- 是否意外加入 API 密钥、令牌、私人路径或私人数据。
- README 描述是否与当前源码行为一致。
- 最新用户要求是否已经进入最终 `main.js`。

仅修改文档时可以不重新构建插件，但更新源码或样式后必须重新构建。

## 9. 双包交付规范

需要同时交付插件和源码时，生成两个独立 ZIP。

### 安装包

ZIP 内必须只有：

```text
agent-dashboard/
  main.js
  manifest.json
  styles.css
```

### GitHub 源码包

应包含：

- `src/`、`manifest.json`、`package.json`、`package-lock.json`。
- TypeScript、ESLint、esbuild 和版本脚本。
- README、LICENSE、CONTRIBUTING、CHANGELOG 和 `docs/`。
- `.github/workflows/` 和 Issue 模板。

不得包含：

- `node_modules/`。
- `.git/`。
- 本地技能目录、代理说明或私人工作区文件。
- 旧的 `release/`、`delivery/`、测试 Vault 或私人数据。
- 根目录构建产物 `main.js`；该文件由发布工作流构建并附加到 Release。

## 10. 交付核验

交付前必须：

1. 列出两个 ZIP 的内容。
2. 确认安装 ZIP 只有三个插件文件。
3. 确认源码 ZIP 包含文档、工作流和完整源码。
4. 比较安装目录文件与根目录构建文件的哈希。
5. 为两个 ZIP 生成 SHA-256，并写入 `SHA256SUMS.txt`。
6. 不覆盖旧发布物；使用新的版本化 `delivery/` 目录。
7. 明确说明是否创建了 Git 提交、标签或远程发布。

## 11. 发布前人工检查清单

- [ ] 插件名称、ID、版本和作者正确。
- [ ] 欢迎语默认值及可编辑状态符合最新要求。
- [ ] 所有未实现功能均显示“即将实现！”。
- [ ] 没有虚假实时数据、固定同步时间或固定任务完成率。
- [ ] 未配置目录、空 Vault 和错误状态可区分。
- [ ] 任务创建、完成、删除、排序和文件标记保护可用。
- [ ] 桌面端浅色、深色和键盘操作已测试。
- [ ] 移动端主要触控目标达到 44×44 像素。
- [ ] `npm run build` 通过。
- [ ] `npm run lint` 无错误。
- [ ] 生产依赖审计无漏洞。
- [ ] README、CHANGELOG 和实际功能一致。
- [ ] 安装 ZIP 与 GitHub 源码 ZIP 内容正确。
- [ ] SHA-256 已生成并复核。

## 12. 本规程的维护

每次发布后，只把已经实际出现且可复用的流程经验补充进本规程。不要为尚未发生的复杂场景提前增加审批层级。规程发生变化时，应同步到下一份 GitHub 源码交付包；只有运行时代码或样式变化时才需要重新生成安装 ZIP。
